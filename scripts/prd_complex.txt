## Problem Definition: 3-Class Swing Classification

**Target Variable**: `testmode` - A categorical variable representing table tennis swing types.

**Classification Task**: A 3-class classification problem with the following target classes:
-   **Class 0**: "Air Swing" - Practice swings performed in the air without ball contact.
-   **Class 1**: "Full Power" - Maximum intensity shots with full power stroke technique.
-   **Class 2**: "Stable" - Controlled, stable hitting with consistent technique.

**Practical Application**: This classification **will enable** coaching feedback by automatically distinguishing between practice motions, power shots, and controlled techniques from wearable IMU sensor data.

**Dataset Context**: Each row in `data/raw/assignTTSWING.csv` represents one table tennis swing motion with pre-computed statistical features from 6-axis IMU sensors (3-axis accelerometer + 3-axis gyroscope), labeled with the corresponding `testmode` value (0, 1, or 2). The `id` column represents the unique player identifier.

## Group-Aware Data Partitioning (Nested Cross-Validation)

To ensure robust model evaluation and prevent data leakage, the project **will implement** a nested cross-validation strategy:

*   **Outer Loop**: A single `GroupShuffleSplit` (e.g., 80% train/20% test) **will be used** to create a final hold-out test set. The `id` column (player identifier) **will serve** as the grouping variable, ensuring that data from any single player does not appear in both the outer training and outer test sets. This split **will provide** an unbiased estimate of model performance on unseen players.
*   **Inner Loop**: Within the outer training set, 5-fold `StratifiedGroupKFold` **will be employed** for hyperparameter optimization. This strategy maintains class balance (`testmode` distribution) across folds while keeping all swings from a particular player (`id`) within the same fold. This prevents overly optimistic performance estimates that could arise if player-specific patterns were learned during training and then seen in a validation fold from the same player.

**Final Ratios (Approximate)**: Based on the outer split, the project will have ~80% of data for training and hyperparameter optimization (further split by the inner CV) and ~20% for the final unbiased test.

**Critical Design Decisions**:
-   **Group Column**: `id` (player identifier) ensures no player's data spans across splits where it shouldn't.
-   **Stratification (Inner Loop)**: Maintains class balance (`testmode` distribution).
-   **Deterministic Splitting**: A fixed random seed (e.g., 123) **will be used** for reproducibility.
-   **Leakage Prevention**: This nested, group-aware approach is crucial for preventing player-specific swing patterns from leaking between training, validation (during HPO), and final test sets.

**Rationale**: Standard train/test splits or naive k-fold cross-validation can fail with grouped data because:
1.  Players often have consistent, idiosyncratic biomechanical patterns.
2.  Random splitting can place data from the same player in both training and testing sets.
3.  This leads to models learning player-specific quirks rather than generalizable swing characteristics, resulting in overly optimistic performance estimates.
4.  The proposed `GroupShuffleSplit` (outer) and `StratifiedGroupKFold` (inner) strategy mitigates this by ensuring complete player separation at critical stages.

# Core Features

*   **Enhanced ETL Pipeline - Signal Processing + Data Quality**
    *   **Location**: `src/etl.py` - This module **will implement** a production-ready ETL process with comprehensive logging.
    *   **Input**: `data/raw/assignTTSWING.csv` containing raw table tennis swing data.
    *   **Target Preservation**: The `testmode` column integrity **will be** maintained throughout all transformations.

    *   **Signal Processing Pipeline (Week 3 Concepts)**:
        *   **Unit Conversion (Physics-Based)**: Raw LSB values **will be converted** to physical units using sensor specifications.
            -   Acceleration [g]: LSB × (2g / 32768) for ±2g range sensors.
            -   Angular rate [°/s]: LSB × (250°/s / 32768) for ±250°/s range sensors.
            -   *Rationale*: Enables physically meaningful outlier detection and cross-sensor comparison.
        *   **Median Despike (Signal Smoothing)**: A 3-point rolling median **will be applied** to remove single-frame sensor spikes.
        *   **Butterworth Low-Pass Filter (Signal Smoothing)**: A 5th-order filter with a 20Hz cutoff (fs=200Hz sampling) **will be implemented** using zero-phase `filtfilt` to preserve signal timing while removing high-frequency noise.
            -   *Rationale*: IMU sensors are susceptible to electromagnetic interference and mechanical vibrations; this step aims to mitigate such noise.

    *   **Advanced Data Quality Rules**:
        *   **Missing Data Handling**: Linear interpolation **will be applied** to isolated numeric gaps before any remaining NaN-containing rows are removed.
        *   **Categorical Cleaning**: Rows with '???' placeholder values in demographic categories **will be removed**.
        *   **Physically-Motivated Outlier Removal**: Samples where the Euclidean norm of acceleration (‖acceleration‖) exceeds 16g (after unit conversion) **will be dropped**.
            -   *Rationale*: Table tennis motions rarely exceed 8-10g; values >16g likely indicate sensor malfunction.
        *   **Feature Engineering (Initial)**: Categorical demographics (age, playYears, height, weight) **will be** one-hot encoded.
        *   **Column Pruning**: Temporal metadata (date, fileindex, teststage, count) **will be removed**.

    *   **Quality Assurance**:
        *   **Deduplication**: Exact duplicate rows **will be removed** early in the pipeline.
        *   **Target Validation**: The integrity of `testmode` and its class distribution **will be verified**.
        *   **Signal Processing Validation**:
            -   Frequency Analysis: Pre/post-filter power spectral density comparison.
            -   Filter Response: Verification that the Butterworth filter meets its 20Hz cutoff specification.
            -   SNR Assessment: Signal-to-noise ratio evaluation before/after filtering.
            -   Outlier Statistics: Logging of removal counts and impact on distribution.
            -   Unit Conversion Checks: Validation of physical ranges.
            -   Temporal Integrity: Ensuring no phase distortion from zero-phase filtering.
        *   **Visualization Artifacts**:
            -   Before/After Signals: Sample swing trajectories showing filter effects.
            -   Frequency Spectra: Power spectral density plots for each processing step.
            -   Outlier Detection: Histogram of acceleration magnitudes with thresholds.
            -   Missing Data: Plots for assessing interpolation quality.
        *   **Comprehensive Logging**: Detailed logs of every transformation step with statistics.
        *   **Output Validation**: The final dataset **will be validated** as ready for GroupStratifiedKFold + scikit-learn.

*   **Group‐Aware Data Partitioning (Nested CV)**
    *   **Implementation**: `src/split_data.py` **will handle** the outer split. Inner splits **will be managed** by hyperparameter optimization scripts.
    *   **Fundamental Principle**: Prevent data leakage by ensuring no `id` (player) appears in multiple splits inappropriately.

    *   **Nested CV Strategy**:
        *   **Outer Loop**: `GroupShuffleSplit(n_splits=1, test_size=0.20, random_state=123)` using `id` as the group.
            -   This single 80/20 split **will create** the final, unbiased test set.
            -   Hyperparameters selected by the inner loop **will be frozen** before evaluation on this test set.
        *   **Inner Loop**: `StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=123)` using `id` as the group and `testmode` for stratification.
            -   This **will be used** within the outer training set for hyperparameter optimization.
            -   It **will maintain** class balance while keeping a player's swings together within a fold.

    *   **Critical Design Features**:
        *   **Group Isolation**: `id` grouping prevents player-specific overfitting.
        *   **Class Stratification (Inner Loop)**: Maintains `testmode` distribution.
        *   **Deterministic Splitting**: Fixed random seed (123) for reproducibility.

    *   **Technical Implementation**:
        *   Libraries: `sklearn.model_selection.GroupShuffleSplit`, `StratifiedGroupKFold`.
        *   Group Column: `id`.
        *   Target Column: `testmode`.
        *   Index Persistence: `splits/outer_train.json` and `splits/outer_test.json` **will store** row indices for the outer split.

    *   **Validation Benefits**:
        *   Realistic Performance: Estimates generalization to new players.
        *   Prevents Overfitting: Avoids memorization of player-specific patterns.

    *   **Documentation**: Splitting strategy and rationale **will be detailed** in `DOCUMENT.md` Section 3.2.

*   **Three-Stage Leak-Proof Pipeline Architecture**
    *   This architecture **will be applied** within each inner CV fold during hyperparameter optimization and for the final model training on the full outer training set.
    *   **Stage 1: Fold-Internal Preprocessing & Feature Engineering**
        -   Each inner-CV split **will build** a fresh Pipeline:
            ```python
            # Example for LR/GP
            steps = [
                ('feature_eng', FeatureEngineer(...)), # Custom feature engineering
                ('selector', SelectKBest(...)),         # Feature selection
                ('scaler', StandardScaler()),          # LR & GP only
                ('pca',    PCA(n_components=0.95)),    # GP only
                ('est',    model_specific_estimator)
            ]
            pipeline = Pipeline(steps)
            ```
        -   Fitting scalers, PCA, feature selectors, and performing feature engineering *inside* every fold prevents target leakage.
        -   This **will follow** Week 5 cross-validation best practices.
    *   **Stage 2: Core Estimator**
        -   **Will receive** transformed data from Stage 1.
        -   Model-specific configurations **will be applied**.
    *   **Stage 3: Metrics Logger (During HPO)**
        -   **Will return** macro-F1 to Optuna for optimization.
        -   **Will persist** artifacts and wall-time per trial.
        -   **Will feed** pruning decisions to `MedianPruner`.

*   **Hyperparameter Optimization Protocol**
    *   **Search Engine**: Optuna 3.0 with `TPESampler` + `MedianPruner`.
    *   **Inner CV**: 5-fold `StratifiedGroupKFold` (groups = `id`, `random_state=123`).
    *   **Objective**: Mean macro-F1 across inner folds.
    *   **Trial Budgets (Planned)**:
        -   LR: 36 trials
        -   RF: 50 trials
        -   LGBM: 50 trials
        -   GP: 20 trials
    *   **Early Stopping**:
        -   LGBM: e.g., ≥20 rounds with no improvement.
        -   GP: e.g., Variational ELBO plateau for 3-5 epochs.
    *   **Pruning Strategy**:
        -   `MedianPruner` with appropriate `startup_trials` and `warmup_steps`.
    *   **Reproducibility**: Global `numpy/random/torch` seed (e.g., 123) **will be stored** in study attributes.
    *   **Configuration Management**: Key HPO parameters (trial budgets, pruner settings) **will be defined** in a `config/hpo_config.yml` or similar, loaded by optimization scripts.

* **Enhanced System Components**

  1. **Enhanced ETL Module (`etl.py`)**

     * **Signal Processing Pipeline**:
       - Unit conversion using sensor specifications (±2g, ±250°/s)
       - Median despike filter for artifact removal
       - 5th-order Butterworth low-pass filter (20Hz cutoff)
       - Linear interpolation for isolated missing values
     * **Data Quality Assurance**:
       - Physical outlier detection (‖acceleration‖ > 16g threshold)
       - Categorical cleaning (remove '???' placeholder values)
       - One-hot encoding for demographic categories
       - Comprehensive logging of all transformations
     * **Signal Processing Validation**:
       - Frequency domain analysis (PSD before/after filtering)
       - Filter response verification (magnitude and phase)
       - Signal-to-noise ratio assessment
       - Temporal integrity checks (no phase distortion)
       - Physical range validation post-conversion
     * **Validation Outputs**:
       - Visual diagnostic plots in `validation/signal_processing/`
       - Quantitative metrics in `validation/signal_metrics.json`
       - Quality assessment integrated into ETL logs
     * **Output**: `data/processed/processed_dataset.csv` ready for ML pipelines

  2. **Signal Validation Module (`validate_signals.py`)**

     * **Comprehensive Analysis**:
       - Power spectral density comparison (pre/post filtering)
       - Butterworth filter frequency response validation
       - Outlier detection visualization and statistics
       - Missing data interpolation quality assessment
     * **Sample-Based Validation**:
       - Select representative swing trajectories per player
       - Generate before/after signal comparison plots
       - Compute SNR improvement metrics
     * **Report Generation**:
       - Automated validation report with pass/fail criteria
       - Interactive plots for manual inspection
       - Quantitative metrics summary

  3. **Feature Engineering Module (`feature_engineering.py`)**

     * **Domain-Specific Feature Extraction**:
       - Time-domain statistical features (mean, std, skewness, kurtosis, percentiles)
       - Physical motion features (vector magnitudes, jerk, angular acceleration)
       - Frequency-domain features (spectral energy, dominant frequency, FFT coefficients)
       - Time-frequency features (wavelet coefficients, short-time energy)
       - Cross-axis correlation and PCA features
     * **Nested CV Compatible Design**:
       - All feature engineering performed inside CV folds
       - Consistent feature extraction across train/validation/test
       - No data leakage through feature computation
     * **Multi-Stage Feature Selection**:
       - Univariate filtering (low variance, high correlation removal)
       - Statistical selection (mutual information, ANOVA F-test)
       - Model-based selection (L1 regularization, tree importance)
       - Wrapper methods (Recursive Feature Elimination)
     * **Validation & QA**:
       - Feature correlation analysis and VIF computation
       - Cross-model importance ranking comparison
       - Dimensionality tracking through selection stages
       - Automated feature selection reports

  4. **Nested CV Data Splitting Module (`split_data.py`)**

     * **Outer Loop**: GroupShuffleSplit for unbiased test evaluation
       - Single 80/20 split with player-based groups
       - Ensures final test metrics are not optimistically biased
     * **Inner Loop**: Handled dynamically in optimization scripts
       - StratifiedGroupKFold maintains class balance
       - 5 folds with complete player separation
     * **Reproducibility**: Fixed random seed with deterministic ordering

  5. **Hyperparameter Optimization Modules (`optimize_*.py`)**

     * **Unified Architecture**:
       - Optuna with TPESampler + MedianPruner
       - Inner 5-fold StratifiedGroupKFold CV
       - Fold-internal preprocessing via sklearn Pipelines
       - Macro-F1 objective with trial logging
     
     * **Model-Specific Features**:
       - `optimize_lr.py`: L1/L2 penalty and C parameter search
       - `optimize_rf.py`: Tree ensemble parameters with OOB tracking
       - `optimize_lgbm.py`: Boosting parameters with early stopping
       - `optimize_gp.py`: Kernel parameters with ELBO convergence

  6. **Pipeline Factory Module (`pipelines.py`)**

     * **Leak-Proof Pipeline Construction**:
       ```python
       def create_lr_pipeline(params):
           return Pipeline([
               ('scaler', StandardScaler()),
               ('lr', LogisticRegression(**params))
           ])
       
       def create_gp_pipeline(params):
           return Pipeline([
               ('scaler', StandardScaler()),
               ('pca', PCA(n_components=0.95)),
               ('gp', SparseGPClassifier(**params))
           ])
       ```
     * **Ensures**: Transformers are fitted only on training data within each fold

  7. **Final Training Module (`train_final_models.py`)**

     * **Loads**: Best hyperparameters from Optuna studies
     * **Trains**: Each pipeline on full outer training set
     * **Saves**: Complete pipelines with fitted transformers
     * **Validates**: No data from outer test set is used

  8. **Evaluation Module (`evaluate_final.py`)**

     * **Single Pass**: Unbiased evaluation on outer test set
     * **No Bootstrap**: Avoids multiple testing issues
     * **Comprehensive Metrics**: Macro-F1, confusion matrices, ROC/PR curves
     * **Interpretability**: Model-specific visualizations (SHAP, coefficients, etc.)

# Risks and Mitigations

*   **Risk: Environment Inconsistencies**
    *   *Mitigation*: Explicit `environment.yml` with version constraints.
*   **Enhanced Risk: Pipeline Complexity (Nested CV, Per-Fold FE/Selection)**
    *   *Issue*: Debugging nested CV with fold-internal feature engineering/selection can be challenging.
    *   *Mitigation*: Comprehensive unit tests, detailed logging, clear `Pipeline` definitions in `pipelines.py`, modular custom transformers.
*   **Enhanced Risk: Optuna Configuration**
    *   *Mitigation*: Explicit configuration, logging Optuna settings, validating pruning.
*   **Risk: Computational Load (Feature Engineering + HPO + GP)**
    *   *Issue*: Extensive feature engineering within each of 500+ (e.g., LGBM) model fits, plus GP training, can be very slow.
    *   *Mitigation*:
        -   Aggressive early stopping/pruning.
        -   Prioritize efficient feature implementations.
        -   `n_jobs=-1` for model training.
        -   Consider reducing trial budgets or feature set scope if time is critical.
        -   Profile feature engineering steps.
*   **Enhanced Risk: Leakage Through Shared State / Incorrect Pipeline Usage**
    *   *Mitigation*: Use `sklearn.clone()` implicitly by instantiating pipelines fresh for each fold/fit, rigorous unit tests for transformer independence and correct `fit`/`transform` sequence.
*   **Enhanced Risk: Signal Processing Quality & Outlier Detection Sensitivity**
    *   *Mitigation*: Comprehensive validation (frequency domain, visual, SNR), literature-based justification for parameters/thresholds, logging impact of choices.
